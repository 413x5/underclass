---
name: underclass-device-auth
description: Add or reauthenticate an underclass subscription through the running server's device authorization flow, using sudo when requested or needed for local service credentials.
---

Use the running server's admin API so successful authorization persists credentials and updates the live pool. The CLI has no account-add command. Do not insert OAuth credentials directly into SQLite or start a second server.

1. Discover the server address and service configuration with `systemctl cat underclass.service`. On this host the service listens at `http://127.0.0.1:8080`, uses `/var/lib/underclass`, and loads an environment file at `/run/overalls-secrets/underclass/environment`. Confirm these rather than assuming other installations match.
2. Read the configured `UNDERCLASS_UI_TOKEN` into process memory using sudo if required. Never print environment files, process environments, tokens, authorization headers, or OAuth credentials. Avoid shell tracing and placing literal secrets in command arguments. A small Python program run under sudo can parse the environment file and send HTTP requests with `urllib.request`; print only selected non-secret response fields. If no explicit token is configured, inspect the configured database read-only for the persisted `config` entry named `ui_token`. Do not mint or replace keys.
3. Check `/admin/api/state` with `Authorization: Bearer <ui_token>` and project only account IDs, labels, backends, and statuses. If the requested identity already exists, report it; use `POST /admin/api/accounts/{id}/relogin` only when reauthentication is requested. Do not create duplicate accounts or delete an existing account as a workaround.
4. For a new account, send `POST /admin/api/flows` with JSON `{"backend":"codex"}` for ChatGPT/Codex or `{"backend":"copilot"}` for GitHub Copilot. Retain `flow_id`. Return `flow.state.verify_url` and `flow.state.user_code` promptly so the user can authorize in their browser with the intended account. The API derives the label from the authorized identity; it does not accept a target email. Browser authorization is a required user step; never claim completion while the flow is pending.
5. Poll `GET /admin/api/flows/{flow_id}` at a modest interval. Pending state contains the verification URL and code; authorized state contains `account_id`; failed state contains a message. Keep user updates within one minute. Stop on authorization or failure. If the code expires or the flow disappears, explain the result and start a replacement only if the user still wants to proceed. Do not create repeated parallel flows.
6. After authorization, query `/admin/api/state` again and match the returned account ID to the requested identity, backend, and status. If the identity differs, report the mismatch without deleting anything automatically. Report success only after confirming the account is present; disclose any unhealthy status.

Keep reusable instructions and commits free of account-specific emails, flow IDs, device codes, and secrets. Commit or push changes only when separately requested. Device onboarding itself requires no source changes, service restart, or deployment.
